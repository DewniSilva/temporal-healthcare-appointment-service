Engineering Guide

Temporal, End to End

What durable execution actually is, when it earns its place in a system, and exactly how this appointment service is built on it.

01

What Temporal actually is

Temporal is a durable execution engine. You write ordinary-looking async code — a function that calls other functions, sleeps, waits for input — and Temporal guarantees that code runs to completion exactly once from the caller's perspective, even if the process executing it crashes, the server restarts, or the wait spans days. No hand-written retry loops, cron jobs, or state-machine tables required.

The mechanism: Temporal doesn't keep your workflow "running" in a process. It records every meaningful thing that happens inside it — a step started, a step finished, a timer fired, a signal arrived — as an event history in its own database. If the worker holding your workflow dies, a new worker picks up the history, replays it (re-executing your function, but feeding back already-recorded results instead of redoing the work), and continues exactly where it left off — new process, same execution.

Hard rule

Workflow code must be deterministic. No Date.now(), Math.random(), or direct DB/network calls inside a workflow — those live in Activities, called through a typed proxyActivities<T>() proxy. This repo enforces the boundary with a real test — tests/architecture.test.ts — that fails the build if a workflow file imports Prisma, fs, crypto, config, or logging.

03

When to reach for it

Use Temporal when a process has two or more of these traits:

  • Steps that must survive a crash between them — not just retry the whole thing from scratch
  • A wait measured in minutes, hours, or days, not milliseconds
  • A need for a human or external signal to arrive mid-process
  • Multiple side effects that must either all stick or be compensated (a saga)
  • A need for at-least-once execution with per-step retries and backoff

Skip it for a plain synchronous request/response, a short pipeline with no external wait, or anything a database transaction alone already makes durable. It's also the wrong call if the team can't tolerate running an extra stateful service — Temporal Server plus its own Postgres.

04

Why it beats the alternative

The alternative to Temporal for this appointment flow: a status column, a cron job polling for reminders due, a queue for retries, a distributed lock to avoid double-processing, a saga table for compensation, and reconciliation scripts for whatever falls through the cracks. Five separate pieces of infrastructure, each with its own failure modes, to reproduce what Temporal gives as one execution model —

  • durable timers, with no polling table for "send this in three days"
  • per-activity retry and backoff, with typed non-retryable errors
  • one place — event history — to see exactly what happened to one appointment
  • workflow-ID collision handling as the idempotency mechanism, instead of a hand-rolled dedupe table

The cost is real too: an extra service to operate, a determinism constraint on workflow code, and a learning curve around replay semantics. See SYSTEM_REPORT.md §4.2 for the fuller trade-off writeup.

05

Building one, step by step

  1. Run Temporal Server — self-hosted via Docker Compose, or Temporal Cloud. Self-hosted needs its own persistence store (Postgres/Cassandra/MySQL) and a visibility store for search.
  2. Define the contract — plain TypeScript interfaces shared by both sides: workflow input/output, activity signatures, signal/query names. Centralized here in shared/temporal/contracts.ts, signals.ts, queries.ts so client and worker can't drift apart.
  3. Write activities — plain async functions with real side effects. Each throws typed errors the workflow's retry policy can classify as retryable or not.
  4. Write the workflow — proxyActivities<T>({ startToCloseTimeout, scheduleToCloseTimeout, retry }) for a typed, retry-wrapped activity handle; setHandler for signals and queries; sleep / condition / Promise.race for durable waits raced against signals.
  5. Run a Worker — Worker.create({ connection, taskQueue, workflowsPath, activities }), then worker.run(). One process, polling the task queue for both workflow replay and activity execution.
  6. Start / signal / query from the API — a Client on the same server and namespace; workflow.start / getHandle / signal / query, using a stable, business-derived workflow ID for idempotency plus a reuse/conflict policy that matches the semantics you want.
  7. Add Schedules for anything cron-shaped, instead of standing up a separate cron container.
  8. Test with time-skipping — @temporalio/testing's TestWorkflowEnvironment asserts on a workflow that "waits three days" without waiting, by advancing a mocked clock.
  9. Instrument it — Temporal ships OpenTelemetry interceptors for worker and client, so workflow and activity spans land in the same trace as the HTTP request that started them.
06

How this system uses it

One workflow per appointment, keyed by a deterministic workflow ID — appointment-<appointmentId> — where appointmentId itself is derived from (userId, idempotencyKey) in appointment.service.ts. A retried HTTP request can never spawn two workflows: workflowIdConflictPolicy: FAIL plus workflowIdReusePolicy: REJECT_DUPLICATE turn a duplicate start into a clean ALREADY_STARTED response instead of an error.

The workflow carries an appointment through a single state machine, from request to a terminal outcome:

Primary path

REQUESTED→ RESERVING→ BOOKED→ CONFIRMED→ COMPLETED
terminal off-ramps — REJECTED BOOKING_FAILED CANCELLED NO_RESPONSE NO_SHOW

Along that path, appointment.workflow.ts:

  • Validates the booking, then reserves the doctor's slot via an activity. If reservation fails, it compensates — releasing the slot and marking BOOKING_FAILED — a saga written by hand in workflow code, not a Temporal-native primitive.
  • Registers signal handlers (confirmAppointment, cancelAppointment, markAppointmentCompleted, markAppointmentNoShow) and a query handler (appointmentState) up front, via setHandler.
  • Repeatedly uses Promise.race([sleep(duration), condition(() => confirmed || cancelled)]) — the idiomatic pattern for "wait until a durable timer fires or a signal arrives, whichever comes first." This is how the confirmation deadline, the upcoming-appointment reminder, and the appointment-time wait are all implemented, with no polling anywhere.
  • Separates retryable infrastructure failures from genuine business conflicts via nonRetryableErrorTypes on the activity proxy — DOCTOR_UNAVAILABLE fails fast, a transient DB error retries with backoff.
  • Treats reminder sends as best-effort: a failed reminder never aborts the appointment lifecycle. Only the reconciliation sweep retries it later.

A second workflow, reconciliationWorkflow, runs on a Temporal Schedule created idempotently at backend startup (reconciliationSchedule.ts). It sweeps for state the primary workflow couldn't self-heal — stale slot reservations, orphaned reminders, retryable failed reminders, and appointments stuck past their expected transition — logging anything ambiguous for a human rather than guessing. ScheduleOverlapPolicy.SKIP guarantees two sweeps never run over the same rows at once.

The backend never touches worker code — it only imports the shared contracts and talks to Temporal through Client.workflow.start / getHandle / signal / query, a boundary the architecture test enforces mechanically. That separation is what makes a durable, resumable, multi-day appointment lifecycle possible without the API process ever holding a timer, a queue consumer, or an in-memory state machine of its own.
